1The questions

The questions your buyers ask. Asked the same way, every check.

You write them once. Byname sends each one word for word to every surface and model you pick, on a schedule, and never puts your brand name in the prompt. So any two checks compare answer by answer.

2The record

Every answer, kept. With what it cost.

Each check stores the raw answer, who it named and cited, and what the call cost. A call that reports no cost is flagged, never counted as $0. Pick any two checks to see what you gained, lost and moved.

4Graded evidence

Three grades of evidence. Never averaged together.

You pick surfaces, not engines. Byname pins each surface to the endpoint closest to what a person sees there, and labels every answer with one of three grades. Charts keep the grades apart, so a stand-in never passes for the app.

5Search and site changes

Search Console, on the same timeline.

Byname reads Search Console every day with read-only access: clicks, impressions, CTR and position, and brand against non-brand. Merged pull requests and changes you log by hand mark the chart. After Google recrawls a changed page, Byname compares it with control pages you left alone.

/docs/preview-environments

Improved experimental

Logged by hand on Oct 7. Over the 31 days after Google recrawled it, against 2 control pages: position up 4.07 places and CTR up 0.97 points.

Each read subtracts what the control pages did over the same days, so a swing in demand that moved every page cancels out.

6Agents

Ask your agent what you lost.

Agents read Byname over MCP, signed in as you with OAuth and the scopes you tick. REST and MCP call the same code as the web UI, so an agent sees exactly what your team sees.

MCP, signed in with OAuth

Add the URL to Claude Code, Cursor or Claude Desktop. Your browser opens, you tick the scopes, and the agent reads results as you. No key to copy.

# Claude Code
claude mcp add --transport http byname \
  https://byname.example.com/mcp

REST, with scoped keys

Give each script its own key with only the scopes it needs, and an expiry.

# Questions where a surface named someone else
curl https://byname.example.com/v1/gaps \
  -H "Authorization: Bearer $BYNAME_API_KEY"
results:read
Read checks, answers and search data
runs:write
Queue, pause and resume checks
config:write
Change questions, surfaces and settings

7Run it yourself

One container and your Postgres. Your agent can deploy it.

Paste one prompt into your coding agent. It asks for your Postgres URL, creates the project, sets the secrets, then deploys and protects Byname on Unkey. You watch and approve. Provider keys never pass through the agent. You enter them in onboarding.

  1. Add Unkey's MCP server to your agent

    # Claude Code. Other agents: mcp.unkey.com/install
claude mcp add --transport http unkey \
  https://mcp.unkey.com

  2. Copy the prompt and paste it into your agent

    It signs you in to Unkey, asks for your Postgres URL, and does the rest.

  3. Open the link it gives you

    Register a passkey. Onboarding then asks for your brand, your questions and where people ask.

Or run it anywhere with Docker

Docker with Compose v2 starts Byname and Postgres 17 on your machine. Open the link it prints and register a passkey. Self-host Byname covers any other container host, and Deploy on Unkey covers every step by hand.

git clone https://github.com/unkeyed/byname.git
cd byname
echo "ENCRYPTION_KEY=$(openssl rand -base64 32)" >> .env
docker compose up -d --build --wait
docker compose logs app | grep -A2 'Open this link'

  • Your keys

    The Treg token and provider keys are encrypted at rest and never returned by any API. Only an Admin can set them.

  • Your data

    Every answer, its raw response and its cost live in your Postgres. Nothing leaves except the calls you turn on.

  • Spend caps

    A cap per check stops queueing calls once it is spent. An optional monthly cap stops the next check from starting.

  • MIT licensed

    One Go binary with the web UI, REST API, MCP server and scheduler. Fork it, change it, keep it.
